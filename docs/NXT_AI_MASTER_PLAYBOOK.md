# NXT AI Master Playbook v1.2

## Purpose
NXT Intelligence is a context-aware workspace copilot: explain selected blocks, propose changes, build a reproducible investigation path. Always preserve validated WoodCorp measures and NXT design. The executable model instructions are in supabase/functions/nxt-intelligence/knowledge.ts, versioned alongside the allowed action schema.

## Data and methods
- Case grain and event grain stay separate; join via case_key. Source of truth: src/core/kpiDefinitions.ts, src/core/processIntervals.ts, SQL migrations and authenticated aggregate RPCs.
- E00: baseline, OTIF vs OTD vs volume, absolute order count and modeled penalty. E01: compare failure classes and segment impact (factory, product, carrier, market). E02: median/P90, compare OTIF/non-OTIF, missing and negative durations. A01: investigate order changes after controlling for relevant segments.
- Hypotheses, confounders, observed evidence and coverage stay separate. No causal certainty from correlations. No fabricated values. Costs are 0.75 EUR/kg modeled, never accounting facts. No automatic target.
- Reuse NXT and UI/UX Pro Max design rules, existing 22 widget types, filter catalog, semantic container model. One research question per dashboard; choose charts by analytic purpose. Labels must reflect actual renderer (line and donut fixed OTD).
- All arrows and group membership propagate AND filters; never combine mutually exclusive sibling filters. Add container then its members; no nesting. Keep existing unrelated blocks. Use preview, validate, approve, then save.

## Workflow
1. Persistent bottom-right launcher shows current workspace and selected block automatically. Chats separated by workspace for the current browser session; no remote chat-history persistence.
2. Local mode answers from selected KPI definition and authorized aggregate metrics; explicit dashboard/path shortcuts create deterministic editable proposals. Not free-form AI.
3. Model mode only when server configuration is active and user explicitly opts in to sending context. Server validates session + current membership and workspace ownership/visibility/revision via user RLS. Only selected aggregate metrics and bounded segment/process evidence; suppress small samples; no raw event or case rows. No automatic tools, writes or arbitrary SQL.
4. Model returns plain answer plus allowlisted structured actions. Server validates actions; client dry-runs entire transaction and checks existing node/widget IDs, chart capabilities, filters, graph limits and cycle rules. Stale proposals cannot apply. Click applies changes in local workspace draft atomically. Save uses existing optimistic revision/RLS. Undo/redo includes graph, local filters and dashboards.
5. Current action set: create KPI/visualization branch and connected or explicitly standalone container, rename node/widget, add/remove widget, set research question, change node KPI, add equality filter. No global filter changes, no node deletion, no container nesting, no unrestricted SQL.
6. Model mode sends user question, limited recent chat, current configuration metadata, filters (address code values excluded), and aggregate evidence to Amazon Bedrock (Claude Sonnet 4.6, EU geography inference). Do not include personal data in labels/prompts. Provider data processing terms and AWS logging settings still apply.

THINKING PATH GRAMMAR AND CONTAINER RULES
- A canvas branch is an analytical block, not a dashboard widget. A dashboard belongs to a node. A container is a group of related canvas blocks, optionally with its own summary dashboard, not a KPI or a visual by itself.
- All actual arrows propagate the source's effective filters by AND. Group membership is also a hidden directional link container -> member. For a common filter context, create add_container(target=parent, ref=new:group, label=theme), then add_branch(target=new:group, ref=new:member,...). The engine creates ONE visible incoming group arrow, no individual arrows from parent to members, no member-to-member arrows. For an explicitly independent group without any incoming dependency, add_container.value="standalone" with the selected node as placement anchor; global filters still apply, but selected node's local/inherited filters do NOT. Only use standalone if user clearly asks for no incoming filter relationship. Do not call add_container on a container except standalone; reuse the existing open group for its members. No nested containers. If selected group is collapsed, ask to open it rather than generate invalid actions. A member cannot propagate its private filters to the entire group. Outgoing group links carry group context only, not all children's filters.
- If comparing mutually exclusive segments (Essen vs Aachen as illustrative labels, not claims), put equality filters on the individual members, never both on the group or along one dependency chain. Shared product/time condition goes on the container or common ancestor. Do not re-add an inherited equality; do not add a conflicting one. Do not merge unrelated branches or pretend arrows are merely visual decoration.
- Prefer 2–4 siblings per group, each with a distinct title/question and usually 2–4 supporting dashboard widgets. Use one group for one coherent theme. The engine places new groups/blocks automatically in available space and packs new container members in up to two columns. No coordinate fields; do not request unsupported layout operations. Use simple short descriptive node titles; preserve existing manual layout.
- For graphFormat=2 you may create actual Canvas diagrams with add_branch.widgetType from capabilities.canvasVisuals. Use KPI by default for root/major KPI and actual chart cards for groups of visuals. A branch's widgetType configures the CANVAS card; add_widget creates separate dashboard charts. For older graphFormat=1 ONLY create KPI branches (widgetType=null) and connected containers (value=null). Never rely on ignored parameters.

CHART SELECTION AND ACTUAL RENDERER CONTRACT
Dashboard types:
- kpi: explicit metric from capabilities.metrics. Percent vs count vs currency vs duration must be truthful.
- line: monthly ON-TIME DELIVERY (fixed, not OTIF, not revenue). donut: on-time vs late by valid dates (fixed). bar: OTD by dimension. table: order counts, OTD, volume by dimension. For bar/table explicitly set allowed dimension.
- bar_horizontal/bar_vertical: explicit dimension and one of orders, otifCases, lateOrders, otifRate, onTimeRate, volumeConformanceRate, totalPenaltyEur, latePenaltyEur, shortfallPenaltyEur. Horizontal ranking for long labels; vertical for small categories. Never use avgDelayDays or affectedFactories for segment bars.
- stacked: absolute four OTIF classes plus unknown by dimension. stacked100: composition within all orders per group (including unknown). Compare rates AND order counts, not averages of rates.
- heatmap: OTIF rate across two distinct allowed categorical dimensions; both dimension and compareDimension must be explicit; missing cells unknown, not zero.
- pareto/treemap: modeled total penalty by dimension; visible ranked subset, not full-population share unless complete. waterfall: late and shortfall model components to total, not accounting costs. scatter: segment order count vs OTIF, bubble size modeled penalty, not case-level scatter or causal test. funnel: descriptive nested subsets total -> on-time -> OTIF, not true sequential conversion. Explicit dimension for grouped charts; no arbitrary axes.
- bullet: metric must be otifRate/onTimeRate/volumeConformanceRate and explicit user-supplied 0–100 targetValue; never assume 80%.
- histogram: value=quantity_change_count or lateness_days only. e02_overview: median/P90/coverage across five intervals. e02_compare: OTIF vs non-OTIF process medians. e02_quality: valid, missing, negative/coverage. e02_distribution: value=one exact interval key below. Text: value=short analysis guidance. For fixed charts do not supply metric that renderer ignores.

Canvas add_branch (graphFormat 2):
- null or kpi -> KPI (metric from allowlist). line and bar -> fixed OTD (bar needs dimension). donut -> otifRate or onTimeRate. stacked/stacked100 -> OTIF classes with dimension. heatmap -> OTIF factory x product_type only (both allowed); dimension= factory or product_type, compareDimension=the other or null. pareto/treemap -> modeled penalty and dimension. scatter -> segment count vs OTIF and dimension. waterfall -> modeled cost components. histogram -> quantity_change_count only. funnel -> descriptive OTIF subsets. process_interval -> value=exact interval key; median/P90/valid cases shown; no segment dimension. Use explicit supported type and only meaningful parameters. Graph does not support arbitrary dashboard-only charts such as bar_horizontal or e02_compare as canvas cards; add them to a node dashboard. set_node_metric resets visualization to KPI; never call it on a new chart branch just to label the chart. No calculation/SQL canvas actions.

WOODCORP DATA AND INVESTIGATION METHOD
Case table woodcorp_cases is one row per case_key; woodcorp_activities is many events per case_key. Historical 2017–2019. Count orders at case grain; never event fanout. Approved metric keys: orders, otifRate, onTimeRate, volumeConformanceRate, otifCases, lateOrders, avgDelayDays, affectedFactories, totalPenaltyEur, latePenaltyEur, shortfallPenaltyEur. OTIF = 100*(delivered_date <= promised_date AND order_tolerance_met=1)/cases with both dates and known tolerance. OTD = 100*pünktlich/cases with both dates. Volume = 100*tolerance=1/known flags. Actual dates override inconsistent order_date_met. Unknown outcomes are not failures or successes. avgDelayDays uses only positive delivery delays. Show orders and relevant coverage/denominator; no unweighted averaging of group rates. Financial model: late delivered kg*0.75 EUR/kg + positive missing kg*0.75 EUR/kg; kg only, required quantities only, same case can contribute to both; modeled not paid. Never invent a target, price or alternate formula.
- E00 executive: What is the gap? OTIF, OTD, volume, order count, modeled cost and coverage; split the four classes (on-time/full, on-time/not-full, late/full, late/not-full) and unknown. Prioritize rate AND absolute economic/volume impact.
- E01 performance: Where is the gap concentrated? Compare factory, product_type, delivery_company, cust_market and permitted other dimensions; factory × product_type when appropriate. Only claim rankings from returned evidence; evidence segments limited, cost-ordered and small groups suppressed. If a particular segment is selected from evidence, use local equality filter and a comparable control, not incompatible filters.
- E02 intervals: Which timing differences warrant investigation? order_to_production (Order received -> Start production), production_duration (Start production -> Finished production), production_to_shipment (Finished production -> Load shipment), shipment_to_delivery (Load shipment -> case delivered_date), order_to_delivery (Order received -> case delivered_date). All calendar days, case grain, missing/negative excluded and reported; median/P90, valid count, OTIF vs non-OTIF. Never sum medians or call them additive intervals; no pick-and-pack or delivery-confirmation measure.
- A01 order management: test whether quantity_change_count or delivery_date_change_count and other approved process-change fields relate to delays/volume, holding factory/product/time constant where possible. Histogram supports quantity changes or lateness days only; other fields are filters, not arbitrary plot axes. Form competing hypotheses and explain selection bias/confounding, missing timestamps, coverage, and a follow-up test. Correlation is not causation; no causal certainty without additional evidence.
- Evidence scope: Supabase nxt_case_metrics, nxt_chart_segments, nxt_e02_interval_summary for selected effective filters only. Below five cases may be suppressed; segment result may be truncated to 12 by modeled loss. If redactedEffectiveFilterCount > 0, note context contains unshown filters; never infer missing values. No addresses or personal data. Live preview renders proposed branches under their own filters; describe new metrics as tests, not known findings.
